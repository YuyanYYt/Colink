# Live 局部关系重绑与局部索引发布

用户确认先完成局部更新。保持现有符号查找、字面文本搜索、源码读取及结构工具，
本轮没有引入 FTS5。当前首选恢复基准继续是 build 19：
`anchor/colink-0.5.0b5-build19-verified`，见 [恢复说明](RECOVERY_0.5.0b5_BUILD19.md)。

## 更新流程

1. 发现文件和校验原源码。路径、哈希、解析器版本及来源不变的文件保留完整解析缓存。
2. 在同一个 SQLite 的 `li_binding_cache` 保存声明摘要、解析缓存摘要和每文件解析时
   实际查询过的绑定输入。包括不存在的模块/名字，不能只跟踪已成功的关系边。
3. 普通函数体编辑重解该文件。声明、导入、类型、重导出目标变化时比较观察输入，
   重绑受到影响的文件；新模块/新导出可以使旧的未解析引用失效后重新解析。
4. 未影响的文件保留数据库中的解析、符号和关系记录；只加载声明摘要用于静态绑定。
   如受影响文件源码未变，只重载该文件的完整解析事实，不重新读取和解析其源码。
5. 单个 `BEGIN IMMEDIATE` 事务更新项目当前 manifest/统计、变化文件和受影响关系，
   清除删除文件。项目父记录保留，未变行不通过外键级联删除。任何异常整体回滚。

事务提交前继续检查来源、授权、读取上下文和源码清单；局部发布也检查基准 manifest。
查询前后仍保留完整新鲜度校验，文件监听不能代替校验。旧上下文仍明确拒绝。

## 回退完整发布

首次构建、旧索引版本、摘要缺失/损坏、源码根或根排除规则变化、不稳定内容排除、
扫描/解析/索引预算受限时采取完整发布。已有内容防护继续生效，部分覆盖不会冒充完整。
摘要自身有独立 16 MiB 上限，超限只关闭局部优化，继续原有有界索引能力。

摘要与原解析缓存绑定并带有全项目摘要校验，缺失行及损坏行均不会作为有效依据复用。
全量解析规则仍为静态 Python/Java，动态分派或外部源码不新增推断。

## 存储与恢复

每项目仍只有当前一个 `live-index.sqlite3`，摘要增加一张表，不增加独立 FTS、图数据库、
文件历史代次或项目源码目录内的文件。500 MiB 是主数据库的磁盘上限；DELETE journal
沿用临时磁盘预算，不代表预分配或 RAM 限制。每项目 200,000 事实和其他预算不变。

表结构是增量增加的派生元数据，原核心表及应用 ID/schema 版本不变。索引版本单独更新，
安装后首次结构请求重建一次本项目当前索引。build 19 仍可打开数据库，发现版本不一致
后重建自己的事实；不通过清空用户数据绕过兼容检查。镜像历史索引不改发布语义。

## 验证边界

定向测试比较全部核心事实行及调用图/依赖图，与新数据库的全量重建一致；另通过 SQL
失败注入确认父记录/无关文件不删除、发布中途失败后的所有表保持原样。
5,000 文件运行时基准已通过发现、监听、更新、旧上下文拒绝、多项目及重启检查。
详细测试、速度对照和安装结果见下文。
