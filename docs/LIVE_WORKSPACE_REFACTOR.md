# CoLink · 多项目工作区与原文件直读重构计划

记录日期：2026-10-06。本文保留最初需求、执行顺序与验收基线。

实施补充：已获完整授权，`codex/colink-controlled-write` 推进到未发布 `0.5.0b1`。
R1～R4/写入核心及真实样例网页主链路有证据，最终 R5/R6/交付门槛仍有待验项。
当前状态与逐条证据见 [REFACTOR_ACCEPTANCE.md](REFACTOR_ACCEPTANCE.md) 和
[IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md)。下方「本次仅记录」「尚未实施」
保留设计时事实，不以它们覆盖最新进度，也不降低原验收要求。

本次仅记录设计，不改运行代码，不监听新的工作目录，不增加网页访问范围，不启用写入，
不更新安装版或网页连接，不删除镜像、配置、数据库或生成物。当前开发源码与维护者安装
基线为 0.4.3，仍是单项目镜像读取；公开安装包的状态继续以 README 为准。

## 1. 用户目标与本轮结论

1. 一次在本机选择一个工作目录，其中可以包含 A、B、C、D、E、F、G 等大型项目；
   不再为了询问不同项目而反复切换菜单栏文件夹、重启隧道。
2. 网页端通过项目列表知道当前连接允许读取哪些项目。用户说“读取 A”，AI 选择 A，
   之后的概览、搜索、源码与关系查询都限定在 A，不顺便加载 B～G 的源码。
3. 重构顺序固定为：**先解耦，后迁移原文件按需直读，再完成多项目工作区与按需索引。**
4. 本机直读模式不长期维护整库源码副本；保留必要的项目登记、文件校验信息、关系索引
   和未来写入的有界恢复材料。“没有整库镜像”不等于“完全不占内存或磁盘”。
5. 正常使用假设是分析期间用户不主动改文件。这个假设不能代替变化检测；AI 自己写入后，
   下一次操作也必须使用新的内容依据。低延迟监听不等于每次读取/写入前内容必定最新。
6. Python / Java 继续作为结构关系优先支持语言；源码仍按需返回文本，不把索引当成源码，
   不承诺完整动态调用关系，也不把整个工作目录一次塞进模型上下文。
7. 后续写入继续遵守默认关闭、先保存再写、多轮多文件整项回退、幂等、中断恢复和容量
   约束；本计划不是写入实施授权。具体契约见 [WRITE_CONTRACT.md](WRITE_CONTRACT.md)。

如果原文件直读可靠且分析期间文件不变，完整镜像对“读取当前源码”不再提供必要的独立
能力。现有代码依赖镜像是迁移成本，不是产品必须保留镜像的证明。是否保留历史源码对照，
须单独处理，不能把它与当前源码入口混为一层。

## 2. 当前实现的真实边界

| 现有位置 | 已确认的限制 | 重构含义 |
| --- | --- | --- |
| `src/code_context/desktop.py` 的 `desktop_binding` | 一个选中根目录绑定一份 project/data/profile | 改为工作区入口及项目登记，不把工作区直接伪装成一个巨大项目 |
| `src/code_context/local.py` 的 `LocalMirror` | 一个根目录、一个项目、一个来源状态 | 拆开来源访问、变化监听、索引与镜像适配器 |
| `src/code_context/server.py` 的 `build_mcp` | 当前本机连接有单项目 `project_scope` | 改为已授权项目集合；每次请求仍必须明确项目 |
| `src/code_context/storage.py` 的读取/搜索 | 源码来自 `files` / `blobs` 和镜像状态 | 将读取与存储实现解耦，不在工具处理器中直接依赖镜像 SQL |
| `src/code_context/intelligence_queries.py` 的 `read_symbol` | 符号位置与源码来自同一镜像 revision | 直读时先确认索引对应的文件哈希，不能沿旧行号读新源码 |
| `src/code_context/intelligence_index.py` 的 `build_index` | 索引构建在镜像事务内，并遍历镜像源码 | 保留解析/绑定算法，改由独立生产端提供有界内容与索引代际 |
| 当前 `snapshot` / `previous` / `get_diff` | 保留期间是不可变历史内容 | 直读上下文不是历史副本；必须显式处理兼容和语义迁移 |

可以继续复用菜单栏生命周期、私有隧道、品牌与运行身份、静态解析/关系分析算法、文本
分页和大部分过滤策略。复用不等于无需回归；本计划不替换官方 SDK 或增加任意终端执行。

## 3. 目标架构与解耦边界

以下名称是设计职责，非当前已实现模块或已定稿 API：

| 职责 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `ProjectRegistry` | 工作区内项目候选、已授权项目、名称/别名、根路径与来源身份 | 不遍历全部源码，不用名称拼接文件路径 |
| `ProjectRouter` | 将明确的 `project_id` 路由到唯一已授权根目录 | 不模糊选择权限，不跨项目兜底 |
| `SourceAccess` | 有界安全读取、文件身份与内容校验、原文/分页访问 | 不保存永久整库全文，不执行项目代码 |
| `ReadContext` | 关联项目、来源绑定与已读取文件的内容依据，检查上下文失效 | 不冒充文件系统原子快照，不永久复制整仓 |
| `WatchCoordinator` | 项目发现事件、路径变化、索引失效、漏事件补偿与后台任务调度 | 不因一个事件全量采集所有项目 |
| `CodeIndexService` | Python/Java 按需解析、绑定、关系查询及有额度的派生缓存 | 不把旧索引包装成当前事实，不随解析缺口禁止普通文本读取 |
| 镜像适配器 | 过渡期承接现有不可变镜像与 HTTP 同步模式 | 不成为新写入核心必须依赖的内容来源 |
| `WriteCoordinator` / `RecoveryStore` | 后续受控写入、任务日志、副本和恢复 | 当前阶段不实现；不借缓存回收删除恢复必需材料 |

```text
本机明确授权的工作目录
        │
        ├── 项目发现 / 登记：A、B、C、D、E、F、G
        └── 变化监听：项目与文件失效信息，不复制整库全文

网页 MCP 请求：project_id + 项目内相对路径/符号 + 读取上下文
        │
        ▼
项目路由与范围检查
        ├── 原文件安全直读 → 返回所需源码
        └── 按需关系索引 → 校验对应内容 → 返回有界结构事实

未来写入请求（本机开关与实施确认后）
        ▼
真实原文件核验 → 独立恢复区 → 精准提交/读回 → 索引失效与更新
```

先让 MCP 面向职责接口，再替换实现。不能一边新增写入，一边无计划地删除镜像表和原有
来源锁；旧模式在迁移验证完成前保留兼容入口，避免当前安装版或历史工具语义失效。

## 4. 多项目工作区：发现、名称与实际隔离

### 4.1 发现项目，而不是把每个文件夹都叫项目

- 本机选择工作区根后，先有界发现候选项目；不递归打开全部文件内容。
- `.git` 目录/标记文件、`pyproject.toml`、`pom.xml`、Gradle 根配置等可作为候选证据，
  不是唯一判据，也不是执行这些配置的授权。没有标准标记的项目允许本机手动登记。
- 文件夹层级、仓库边界、同根多语言、嵌套仓库和单仓多模块须消歧。默认不把每个
  `src/`、Python 包或 Maven 子模块都注册成独立项目；支持用户明确覆盖边界。
- 项目发现先剪枝依赖、构建、缓存、恢复区、应用数据与符号链接目录；设置发现深度、
  目录数量和执行时间预算。发现不完整时说明原因，不把部分结果称为所有项目。
- 已登记父项目默认不包含独立登记的子项目源码，防止读取父项目时悄悄读取另一项目。
  显式共享/跨项目分析另行确定，不靠路径包含关系扩大范围。

### 4.2 一次设置工作区，不再逐项目切换连接

- 一次本机设置可批量登记并确认 A～G 的可读范围，同一个私有连接服务这组已授权项目。
  选择目录本身不自动启动连接，也不自动把所有候选源码交给网页。
- 后续新发现项目在本机标为“待启用”，默认不静默加入网页读取范围。工作区新增授权
  策略若要自动化，须另行明确；网页工具不能自行增加目录或项目。
- `list_projects` 只列出已授权且对当前连接可见的项目，分页返回名称、唯一标识、必要
  的语言/状态信息；不返回未启用项目的源码、真实凭据或无关绝对路径。
- 工作区根限制仍拒绝系统根、整机/整家目录、路径逃逸和符号链接绕行。项目移走、根
  被替换或卸载时标为不可用，旧读取上下文和写入授权失效，不把临时不可用当批量删除。

### 4.3 名称帮助选择，ID 与根路径决定范围

用户不需要输入内部 ID。AI 从项目列表把自然名称映射到 `project_id`，后续各工具显式
携带该 ID；可以使用目录显示名和本机设定的别名。精确名称/别名优先，关键词匹配仅作
候选选择；同名、多匹配、零匹配必须确认，不能自动读几个项目来猜用户指的是谁。

建议流程（参数示意，实际 schema 在实施阶段定稿）：

```text
用户：“审查 A 项目的某段逻辑”
→ list_projects：确认 A 及其唯一 project_id
→ repo_overview(project_id=A)：开始该项目的读取上下文
→ search_code / read_file / 关系工具：始终使用 A 与同一上下文
→ 回答 A 的代码；切到 B 不需要菜单栏重选文件夹
```

后端对每次读取、搜索、符号和图查询都检查项目 ID、来源绑定、上下文与项目内路径。
unknown ID、A 的上下文配 B、绝对路径、`../B`、符号链接、全库 SQL 漏项目条件都必须
拒绝或安全失败。A 没找到时不能自动搜索 B～G；跨项目引用只能标出外部/不可见候选，
进一步读取需要明确的跨项目请求和对应授权。

隔离保证针对正确确认的项目标识；自然语言路由仍可能选错，须用项目名称回显、歧义
确认和实际网页验收发现错误，不能声称关键词匹配有 100% 理解保证。不要使用全局
“上一次选中的项目”推断请求范围，避免多对话并发串项目。

## 5. 大工作目录的监听与按需索引

“统一监听”指统一掌握项目及文件变化，不是同时全文采集、复制、解析 A～G。

1. 工作区层处理候选项目新增/移除和有限登记信息；项目层把文件事件归属到具体项目，
   合并为失效信息。只监听而尚未查询的项目不提前持有整库源码或建立全部关系图。
2. 用户查询 A 时，源文件只在 A 内按需读取；结构查询需要的解析与绑定也只在 A 内进行。
   文件列表/文字搜索可能需要遍历 A 的允许文件，首次完整关系查询可能要解析 A，
   因此不承诺“任何查询只读一个文件”或“第一次大项目图查询没有等待”。
3. 未变化文件可按内容哈希复用解析事实；定义、导入、源码根或包拓扑变化须重新绑定
   受影响的关系，不能只更新发生编辑的那一条符号。保留既有源码根修复能力。
4. 监听只加速失效检测，不作为新鲜度证明。事件合并、丢失、溢出、启动空档和停机
   编辑都需要补偿；不能继续每 60 秒全文读取 A～G。改用有界元信息对账、项目脏标记
   和目标文件核验；必要的全文工作按项目/任务调度并计量。
5. `watch_filter` 不能被当成操作系统监听资源剪枝保证。须验证大目录下的原生监听资源、
   依赖目录排除、事件吞吐和轮询退化；资源不足时明确降级/报告，不默默保留无界队列。
6. 后台生产端拥有索引更新与补偿任务。MCP 查询可经协调器请求/等待必要的索引状态，
   不在多个工具处理器内各自重建，不借查询修改源码或扩大项目范围。明确调整当前
   “查询只读镜像”的维护约定后，才能实施目标文件直读。
7. 源码已变而索引待更新时，普通直读不冒充旧源码；图/符号工具应等待有界更新，或
   明确返回索引未就绪/不完整。不能把旧行号和当前文件组合成看似正确的结果。

## 6. 读取新鲜度与历史状态迁移

### 6.1 原文件直读的承诺

- 读取最新已保存到磁盘的允许文本，复用安全打开、来源身份、读取前后状态检查与
  内容校验；未保存的编辑器缓冲区不属于读取目标。
- 直读绕过源码镜像同步等待，但不是零延迟、文件系统整库原子快照或项目运行正确性的
  保证。读取中变化、根被替换或文件不可用时明确重试/拒绝，不返回混合内容。
- 一次新分析建立项目绑定的读取上下文；可以只记录必要文件的哈希/指纹，不永久保存
  整库正文。重复读取或使用索引位置时核验对应内容，失效后重新获取支撑结论的源码。
- 新上下文不天然证明尚未读取的所有文件来自同一瞬间。在“分析期间不改动”的正常
  假设之外，跨文件一致性须用参与文件校验/变化检测等机制验证，不能用名字叫
  `snapshot` 就承诺过去的不可变源码还能读取。
- 普通回答不展示递增版本数、上下文 ID 或哈希。工具内部仍保留校验依据和失效语义。

### 6.2 旧 `snapshot` / `previous` / `get_diff` 不能悄悄改变

这是迁移前必须定稿的兼容点：

1. 解耦阶段原镜像模式的工具语义、保留两份状态和失败语义保持不变。
2. 新直读上下文与旧不可变 snapshot 分开描述和校验，不把“旧标识 + 当前原文件”
   包装成过去的源码。新模式不支持的历史请求必须明确拒绝，不能静默回退到 current。
3. 如要继续保留外部编辑之前的任意历史对照，就必须保存足够旧内容；只有事件通知，
   不能保证在外部覆盖之后再读回其旧正文。不能同时承诺取消全部旧内容和原历史语义。
4. 长期候选是源码直读，加受控任务修改文件的起点/必要旧内容，按需对照与回退，而非
   整库永久镜像。这不能自动等价于旧 `previous`，具体工具兼容/替代方案须确认。
5. 工具名、参数、能力说明、Server instructions 和 Skill 一起迁移；试验新模式可在
   独立样例使用，未确认兼容方案前不把它作为稳定版默认行为替换旧安装版。

现有数据库只作为过渡/历史材料保留；确认功能和迁移方案不构成删除用户持久化数据的
授权。最终若停止镜像，明确停止新镜像写入，再另行列出实际清理对象让用户确认。

## 7. 为后续写入保留的边界

后续写入核心依赖 `SourceAccess`、项目授权、任务状态和 `RecoveryStore`，不依赖镜像
正文作为真实写入依据。原文件是修改目标；索引是派生数据；恢复副本是独立受保护材料。

- 每笔写入明确项目、任务、相对路径、读取时的完整文件校验值、原文/上下文、修改内容
  和幂等标识；先核验真实原文件，预留空间，持久保存副本和日志，提交前复核，再写入
  和本机读回。一次网页工具调用可完成这些本机步骤，无须额外调用“备份工具”。
- AI 已有有效上下文时不机械额外读一遍整个仓库；上下文不足或冲突时读必要范围。
  写入结果提供有界片段、新校验依据和索引状态，供下一笔使用，不沿用旧行号/旧标识。
- 写入已成功而索引待更新要分开报告，不能普通失败后重复插入；同请求重试不重复执行。
  无论读取模式如何变化，写入默认关闭、本机开关与实际用户修改请求仍是独立门槛。
- 本机写入开关须明确授权的项目；允许读取 B 不等于允许修改 B。任务不能通过换一个
  项目 ID 改写别的根目录，范围/来源改变或重启后旧写入授权失效。
- 任务首版绑定一个项目；在 A 内跨轮修改 `a.py`、`b.py`、`c.py` 后整体恢复任务起点。
  不因为共用工作区或相同任务名称就把 B 的文件加入恢复集合；跨项目事务不属于首版。
- 任务—文件—操作记录决定实际恢复集合；依赖图只提示潜在影响，不决定遗漏或顺便
  覆盖哪些文件。首次修改文件前保存起点，同一文件多次修改不永久保留所有中间全文。
- 一次多文件写入/回退操作未完成时，查询与索引发布须协调，不能返回半完成状态作为
  最终结果。普通单文件替换和 SQLite 日志不等于多文件同时原子提交；外部热重载仍
  可能看到逐文件变化，源码回退也不能撤销已发生的网络/数据库运行副作用。
- 哈希检查和 CoLink 自身串行锁不保证对任意外部编辑器完全无竞态；冲突、提交中断、
  磁盘不足及中断恢复必须专项验证，不能以用户平时不改动为由省略。

这与 [WRITE_CONTRACT.md](WRITE_CONTRACT.md) 的恢复保障一致，但改变其“读取继续只查
镜像”的未来实现前提。正式实施前明确更新能力约定，而不是把文档变更视为现已能写。

## 8. 内存、磁盘与配额

- 不为工作区每个项目保存一份全量源码镜像，不长期在 `ScanResult` 类结构中保留 A～G
  的全文。有界读取/解析的瞬时内存、文件清单和关系索引仍需实际计量。
- 项目发现、文件清单、脏标记/事件队列、解析任务、索引/缓存、响应和恢复区分别设置
  限额。工作区设置全局额度，项目也有独立上限，不能切换项目就再获得无限额度。
- 不活跃项目的可再生成索引可按已确认规则淘汰；队列溢出可合并为项目待对账状态。
  不因腾缓存删除源码、配置、凭据、既有镜像数据库或活跃恢复材料。
- 恢复区沿用独立有界策略：保护活跃/冲突/未完成恢复的必要副本，空间不足时拒绝
  新写入。原建议额度见写入契约，仍需结合大型项目重新确认，不因本计划自动生效。
- 当前单文件 4 MiB、文本编码、响应分页、敏感文件排除仍是兼容基线；整份镜像总文本配额
  不应直接变成整个工作目录的总大小限制。直读/索引/恢复各自的额度在实施前明确，
  不默默放开无限文件、无限源码响应或无限备份。
- 报告区分源码规模、逻辑存储、SQLite/WAL、文件系统分配、运行 RAM、峰值和缓存；
  不承诺完全零额外空间，也不在没有测量前承诺某个毫秒数、固定倍数或一定更快。
