## 3. 本轮关键证据与边界

### 3.1 输出预算误报

通过现有连接，在同一个有效 Live 上下文中顺序调用：

```json
{
  "mode": "file_context",
  "selector": {"path": "src/code_context/intelligence_dataflow.py"},
  "include": ["ownership", "dependencies"],
  "max_chars": 6000
}
```

仅改变 `max_chars` 得到：

| 字符预算 | 实际结果 |
| ---: | --- |
| 6000 | 工具错误文本包含 `INVALID_STRUCTURE_QUERY: check bounds, path and symbol identifier`；连接包装返回 `error_code=INVALID_ARGUMENT` |
| 12000 | 返回部分分析，`analysis_status=partial`、`truncated=true`、`truncated_reason=["max_chars"]` |
| 20000 | 返回部分分析，`analysis_status=partial`、`truncated=true`、`truncated_reason=["max_chars"]` |

源码中，[`intelligence_analysis.py`](../src/code_context/intelligence_analysis.py) 的 `bound_analysis_result`（保存基线第 521 行起）会在元数据或单项无法装入预算时抛出 `ValueError`；[`live_index.py`](../src/code_context/live_index.py) 第 879–882 行将 `ValueError/TypeError/AttributeError` 合并为 `INVALID_STRUCTURE_QUERY`。[`intelligence_tools.py`](../src/code_context/intelligence_tools.py) 还承担外层显示名称、源码附带与再次裁剪。

这证明错误分类需要修复。实施时仍需在独立源码环境确认该请求触发的具体底层分支，避免把所有 `ValueError` 都改成预算错误。

### 3.2 已有能力应保留

- [`live_dataflow.py`](../src/code_context/live_dataflow.py)、[`java_dataflow_ast.py`](../src/code_context/java_dataflow_ast.py) 已将 Java 有界值传播接入现有分析入口。Java 数据流不是待从零实现的功能。
- [`intelligence_coverage.py`](../src/code_context/intelligence_coverage.py) 已有结构提取、受限、未分析、元数据遗漏等解释及有界样本；当前语言识别表未列出 Swift，需要补充分类测试，不能据此假称新增 Swift 解析能力。
- [`live_index.py`](../src/code_context/live_index.py) 已有解析缓存、拓扑复用、局部重绑和局部发布逻辑。后续先定位真实瓶颈，不重复建设“增量索引”。
- 当前源码的 `analyze_code` 仍有 13 个 mode。Live 已移除的旧读取/图工具无需重新恢复；Mirror 保留历史接口和语义，见[统一入口说明](CODE_ANALYSIS_ENTRYPOINT.md)。
- 现有 Java 方法引用可提取为 `REFERENCE`；`Type::method` 仍会遇到共享绑定器的表达式限制。提取到文本不等于绑定到目标；声明类型候选不等于确定的 JVM 运行时分派。

### 3.3 安装版与源码分别验收

只读检查 `/Applications/Colink.app/Contents/Info.plist` 得到：`CFBundleShortVersionString=0.5.0`，`CFBundleVersion=34`。这只是当前 bundle 的标识。

抽查安装包内四个同名核心文件：`intelligence_analysis.py` 与当前源码相同；`live_index.py`、`intelligence_dataflow.py`、`intelligence_tools.py` 不同。此次工具复现证明现有连接的实际行为；本轮没有对正在运行的服务进程作可执行文件溯源，也没有证明它与当前源码完全等价。

因此，当前源码的修复验收应使用独立源码副本和新索引目录。安装版仍按 `AGENTS.md` 的当前阶段约定保持运行，不覆盖、不重启。仅比较了上述文件，未执行整包哈希、签名或安装运行验收。

## 4. 修改目标与范围

1. 正确区分输入错误、输出预算不足、计算超时、读取上下文失效及索引不可用，使调用方能够选择正确的下一步。
2. 减少重复编码、重复查询和不必要的图展开，同时保留源码身份与前后校验。
3. 让常见问题以更少的工具选择取得必要关系和源码，按需触发值流。
4. 增强现有 Python/Java 关系及值流证据，保持 `partial/unknown` 的真实边界。
5. 以相同的选择器、事实模型和预算机制扩展 TypeScript/JavaScript 结构分析。

实施范围限定在本仓库。真实读写验收使用 `examples/sample_project` 或仓库内新建的独立测试目录；不修改其他连接项目。保留锁文件、持久数据、恢复记录和已有产物；本计划不涉及终端权限变化、数据库入口变化、整套写入系统重构或安装更新。

## 5. 分阶段修改内容

### M1：预算、错误分类与覆盖解释——首批必做

修改位置：`intelligence_analysis.py`、`live_index.py`、`intelligence_tools.py`、`intelligence_coverage.py`；尽量复用已有错误与裁剪机制。

- 为输出预算不足使用独立异常类型，在 Live 层和 MCP 包装层保持可识别的错误分类。具体公开错误码在实施时统一命名并补契约；本计划不将拟议错误码写成现有能力。
- 对合法但装不下的请求，优先返回可用的部分事实、截断原因和可继续位置；最低限度元数据或单项也装不下时返回明确的预算错误与固定安全提示。
- 真正的无效选择器、非法范围和错误字段继续拒绝。`include=source` 的最小预算要求仍作为输入契约，不能与结果过大混淆。
- 核对结构结果、`index_coverage`、显示名称和附带源码共享外层预算的方式，避免内层成功后被外层元数据再次推过上限。
- 保留全局 `index_partial`，补充选中文件、所需关系及本次查询实际覆盖的解释。图被裁剪后，所有边端点和路径都必须仍有效。
- 扩充 Swift 等语言的识别说明；检测到语言、能够提取结构和能够绑定引用分别报告。

关键验收：

- 复现请求在 6000 字符预算下返回合法部分结果或专用预算错误，不再误报路径/符号参数错误。
- 检查 1000/1600/3000/6000/12000/20000/50000 等预算边界，并分别处理附源码的合法/非法组合。
- 覆盖较大的单符号、文件符号列表、ownership、dependencies、source、Unicode/转义字符和重复定义；分页不能停在原位置而无限续读。
- 上下文失效、源码变化、未知项目、索引不可用和时间限制保留原有拒绝或部分结果语义。

相关现有测试：`test_intelligence_analysis.py`、`test_live_analysis.py`、`test_analysis_source.py`、`test_index_coverage.py`；只补上述缺口及必要交互。

### M2：搜索与查询性能——紧接 M1

主要位置：`read_search.py`；按测量结果涉及 `intelligence_queries.py`、`live_index.py` 或 `intelligence_tools.py`。

- 为单条匹配计算准确 JSON 成本，增量维护已累积结果的字符预算；处理逗号、转义、可变元数据及候选缩短，最终响应仍做准确编码检查。
- 避免每加入一条匹配就重新序列化此前所有匹配；评估把游标签名生成留到真正返回页面时，保持既有游标绑定契约。
- 保持匹配顺序、下一位置、上下文裁剪和 `has_more/search_complete` 的语义；`has_more` 只表示扫描仍可继续，不表示已发现后续匹配。
- 分开测量目录发现、源码验证、文件读取、索引等待、SQL/解码、图计算、裁剪和序列化。使用现有统计与脚本扩展，避免另造常驻监控系统。
- 仅在真实无匹配搜索的主要成本被证明确为扫描后，再评估候选筛选索引。筛选结果必须经过真实文件和当前权限校验；不缓存任意历史正文或跳过源校验。

性能验收采用同机交替顺序的基线/修改版对照，报告原始样本、P50/P95、扫描字节、编码次数、峰值内存和结果等价性。热查询按场景至少 50 次，独立重复两组；冷启动单列，不把少量样本的最大值称为 P95。

初始目标为高匹配场景编码开销明显下降、端到端 P95 力争改善 20%，小项目端到端耗时不持续恶化 10% 以上。这是待基线校准的验收目标，不是已取得的收益；若主要开销在安全校验或 I/O，应据测量调整优化点。

数据集包含本仓库和仓库内隔离的 Python/Java 样例，覆盖少匹配、多匹配、无匹配、长行及不同输出预算。1K/5K 文件用于起步规模，10K 以上只在现有预算和明确测试目标允许时扩展，真实与合成样例分别标注。

相关现有测试：`test_read_search.py`、`test_read_code.py`、`test_intelligence_query_optimization.py`、`test_live_index.py`。复用 `benchmark_intelligence_upgrade.py`、`benchmark_live.py` 的可复现约定；其现有计时并不全都包含 MCP、隧道或模型，最终须另补真实 MCP 请求计时。

### M3：收敛常用分析入口——先确认路由与兼容契约

主要位置：`intelligence_tools.py`、`intelligence_analysis.py`、`live_dataflow.py`、技能和入口文档。

日常分析采用一个主要入口，内部按精确选择器决定必要工作；不通过再增加一个 `auto` mode 来扩充选择面。

| 已提供的选择信息 | 日常入口的拟议行为 |
| --- | --- |
| 文件 | 有界文件结构、归属和必要依赖 |
| 精确符号，无具体值 | 符号上下文及必要关系 |
| 一个具体值 | 该值的来源与影响切片 |
| 两个符号，没有值选择 | 有方向的静态调用路径 |
| 两个具体值 | 值传播路径 |
| 明确请求正文或组合关系 | 在剩余共享预算内附带相应内容 |

- 先设计默认 schema 与旧 mode 请求的兼容适配，验证当前 MCP SDK 是否支持将兼容参数留在服务端而不继续暴露整组日常选择。若不支持，先交付可验证的默认路径，不声称发现面已精简。
- 旧 mode 的有效语义通过适配和金样例保留；不恢复已经删除的 Live 工具，不改变 Mirror 接口。
- 歧义符号返回候选；缺失值选择时只做结构分析，或说明所需选择，不猜具体参数，也不把 `combined` 当作所有请求的全量默认。
- 源码精确读取、字面搜索、静态引用、反向文件影响及值传播继续保有各自语义和按需路径。

验收记录默认发现 schema 大小、必要决策字段、后端查询次数、结果长度及真实 MCP 延迟。用固定常见任务核对路由和旧请求结果；工具数量、schema 缩短与模型实际选择速度分别报告。没有模型端实测时，不宣称 Token、模型延迟或误选率已经改善。

### M4：补强 Python/Java 语义——先提高现有能力质量

主要位置：`intelligence_resolver.py`、`intelligence_java.py`、`java_dataflow_ast.py`、`intelligence_dataflow.py`、`live_dataflow.py`。

- 以同问题的 Python/Java 对照样例建立有限语义矩阵：定义/引用、调用、参数绑定、赋值覆盖、返回值、跨文件 helper、遮蔽、中文位置及受限语义。
- 优先检查 Java 方法引用绑定、静态调用与声明类型候选、重载消歧和业务参数/receiver 区分。只对足够静态证据建立关系；其余保留候选或 unknown。
- 用正确结果和明确限制分别验收：存在静态边、存在 may-flow 路径、路径是否确定、还有哪些分派/副作用未知，不能只检查 `path_found=true`。
- 构造器、字段/容器别名、lambda、异常及循环按独立能力逐项推进，不能以“一次性 Java 全量对等”为验收口号。跨语言 HTTP/RPC 边界保持未知，除非另有接口映射证据。

验收复用 `verify_java_dataflow.py` 的真实 MCP 路径并扩充关键样例；保留既有 Python/Java 正例和正确的拒绝/partial 反例。局部通过不代替任意用户工程或 JVM 运行时证明。

### M5：TypeScript/JavaScript 结构分析——分批新增能力

当前计划的新增语言顺序为 TypeScript/JavaScript，随后按实际使用需求考虑 Swift/Rust。这个顺序属于提案；M1–M4 的收益不依赖同时完成多门语言。

先从 `_language`、`parse_file`、解析版本和覆盖诊断中提取最小前端注册契约，复用 `ParsedFile`、索引存储、选择器及预算。各语言的根解析、导入和绑定规则分别实现，不假设 Python 规则天然适用。

1. **M5a：语法与定义。** 支持 `.ts/.tsx/.js/.jsx/.mjs/.cjs` 中明确范围的函数、类、方法、作用域及源码位置。语法失败、资源超限和暂不支持的构造返回覆盖限制。选定前端及依赖后再更新锁文件和第三方声明。
2. **M5b：模块与引用。** 从项目内可静态确定的 import/export、相对路径和重导出开始；配置只在已授权项目内读取。类型专用引用、同名导出和路径映射分别标明；不执行 npm 脚本或项目模块，不自动抓取外部依赖。
3. **M5c：有界调用关系。** 对证据充分的函数调用建立边；动态对象、回调和框架注入保持 unresolved/possible。接入已有调用/依赖/引用接口，不增加一组按语言命名的 MCP 工具。
4. **后续单独评估：值流与框架。** TypeScript/JavaScript 值流、Vue 单文件组件、模板、React/Vue 框架关系、运行时追踪分别立项；`.ts` 解析通过不表示这些能力完成。

每一小阶段提供固定源码样例、精确期望关系、歧义/未知反例及端到端 MCP 查询。Python/Java 的公共契约保持有效；前端/派生索引版本改变时用新索引验收，不能把旧索引误当新能力。

### M6：Rust、局部解耦与发布溯源——后置门槛

## 7. 提交顺序、依赖与风险处理

建议提交顺序：

1. 当前源码保存点与本计划书，分别提交。
2. M1 预算异常分类及其关键测试，再补覆盖解释；相应代码智能 CI 同步落地。
3. M2 搜索增量预算与等价性验证，再提交实际测量结论；候选索引视结果决定。
4. M3 入口契约与兼容方案核验，通过后实施默认路由、schema 和文档更新。
5. M4 每种 Python/Java 语义一个小批修改与验收。
6. M5a、M5b、M5c 分批提交；M6 按测量收益和发布安排独立推进。

M2 在 M1 的预算契约稳定后推进；M3 使用同一套正确性及性能基线。M4/M5 可以沿用既有 mode 进行后端开发，不应被 M3 的 SDK 适配问题长期阻塞；后续统一日常入口调用相同后端。每阶段完成后以新提交固定成果，失败则停在该阶段分析原因，保留原失败材料和最近通过版本。

主要风险及处理：

- **异常误分类继续扩散：** 新增独立预算异常，保留输入、源变化和存储错误；同时验证最外层 MCP 错误。
- **性能优化破坏分页：** 精确核算 JSON、保留最终编码检查，逐页与基线比较事实和续读位置。
- **入口简化反而计算更多：** 选择器驱动按需计算，比较查询次数和响应体积；值流不无条件启动。
- **静态能力被夸大：** 结构提取、符号绑定、可能分派和值传播分别记录，保留不确定结果。
- **语言扩展污染缓存或根解析：** 显式前端/索引版本，分语言规则，项目内配置和独立新索引验收。
- **源码成功被当作安装/网页成功：** 源码、安装包、当前连接和真实网页各有实际证据后再报告完成。
