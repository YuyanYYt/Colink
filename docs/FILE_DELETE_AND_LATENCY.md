## 单文件删除的契约

`delete_file(project_id, task_id, request_id, path, expected_sha256)` 只用于用户明确要求
删除的单个已声明 UTF-8 源文件；必须有本机项目写入授权和同一项任务。先读取真实
文件并取得完整 SHA256，删除工具内部完成核验、空间预留、持久起点/属性保存、原生
隔离、再次验证、移除和结果登记，不需要单独的「备份工具」。

- 目标以实际内容、完整文件版本、属性和父目录身份核对；旧依据、链接、越界、
  被忽略对象、目录或外部替换拒绝，不提供递归删除、重命名或命令执行。
- 删除不是写入空字符串。任务成员的最新状态记录为不存在，原 `get_diff` 返回
  删除摘要/必要 patch；已创建后又删除的文件不构成任务起点到当前的净新增。
- 第一次触及原文件的起点不被后续小改覆盖。修改后删除、删除后同路径重新创建，
  均保持任务原始起点；重新创建仍不能覆盖外来对象或接管已替换的父目录。
- 同一次请求的相同参数重试返回已登记结果，不再次移除后来出现的外来文件；
  不同操作必须使用新的请求标识。重试结果是原操作回执，不是新的现场删除证明。
- 整项回退先核验全部成员，恢复已删除原文件的正文/原属性，撤销任务新对象；
  外来目标重新出现时拒绝，不先恢复一部分。恢复删除文件使用原子不覆盖创建。
- 中断时保留已登记副本与现场，只通过现有本机恢复链路续做已证明的步骤；未知
  临时对象不强制删除，恢复不重新授予写权限。文件系统逐项提交不等于多文件原子事务。

恢复区继续使用原有上限：64 MiB 常驻、128 MiB 管理峰值、16 MiB 元数据库、
1024 操作/任务、最近一项完成恢复点且最多七天，活跃/冲突/待恢复点受保护。
空间不足在源文件变动前拒绝，不能为腾空间而删除未知材料。此功能不是系统废纸篓
或永久备份；恢复点退休后不能再依靠它恢复文件。

客户端若尚未列出 `delete_file`，不能用清空正文、重命名或整体回退假装单文件删除。
随附 Skill 已增加这条工具可用性约束；网页已安装 Skill 的副本尚未更新。

## 创建文件为什么在网页上等了很久？

真实网页一次 Hello World 创建从消息开始到结束约 **38.710 秒**。本机日志中，
开始任务记录出现在约第 **22.792 秒**，从开始任务到完成任务约 **13.465 秒**，
完成后到最终回答约 **2.453 秒**。这些是整轮和任务边界，不是逐工具网络耗时。

另外用当前已安装 beta.1 的真实 Python/MCP stdio，在独立合成目录重复五次，
不经过 GPT、网页或远程隧道，测得：

| 测量项 | 五次观测 |
| --- | --- |
| 单次 `create_file` | 34.503、34.539、34.430、33.698、48.841 毫秒；中位 34.503 毫秒 |
| 状态→开始任务→创建→读取→完成的完整五调用链 | 115.658、69.011、66.727、67.269、82.090 毫秒；中位 69.011 毫秒 |
| 进程启动与连接准备 | 740.874 毫秒，单独计量，不混入上述调用时间 |

两组结果表明这份微型样例的本机落盘并非数十秒等待的主要部分；仍不能准确区分
模型组织调用、平台调度、网络与隧道各自占比，更不能用合成目录推断大型项目延迟。
本轮没有减少必要备份/读回或伪装只读权限来换速度，也没有声称网页响应已加速。
后续若要优化，应先获取逐工具链路时序，再评估必要调用合并，而不是取消恢复保护。
