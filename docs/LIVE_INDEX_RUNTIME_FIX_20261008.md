## 根因与上一轮验证缺口

已核对实际安装版为 build 18，四个关键后端文件与工作区一致。实际 MCP 符号查询
仍约 4.8 秒返回容量错误；其他四项亦返回同一错误。

实际索引库只有 19 页/77,824 字节、无索引事实，`SQLITE_FULL` 的事务回滚保留了空库。
容量错误发生在构建发布阶段，不能用回滚后的文件大小认定构建只占 76 KiB。

上一轮真实仓库组件验证使用短标识 `review`。同一源码、同一批 84,406 条事实：

| 项目标识 | 主库物理占用 | 结果 |
| --- | ---: | --- |
| 短标识 `mcp` | 55,754,752 字节，约 53.17 MiB | 成功 |
| 实际 34 字节项目 ID | 67,612,672 字节，约 64.48 MiB | 64 MiB 上限失败 |

后一占用只通过独立的 96 MiB 诊断额度取得，未放宽当时安装版。该测试发现
65,512/80,736 条关系没有确定目标符号；空目标和重复项目标识使 SQL 索引明显膨胀。
在复制的诊断数据库上重建非空端点索引后，占用降至约 60 MiB。

因此上一轮隔离成功没有覆盖实际标识长度，不应算第一项最终完成。原报告保留，
本记录补充这次被真实 MCP 复测发现的缺口。

## 修复设计

1. 非空端点 SQL 索引省略 NULL 查找键，保留全部未解析关系及其证据；历史完整索引
   在事务中升级，表结构与旧查询兼容。关系损坏重建和解析格式标记继续保留。
2. 每项目独立 SQLite，只保存当前一版。项目 ID 哈希决定私有存储位置；项目授权
   仍由当前来源校验。用户最终选定每项目主库硬上限 500 MiB，按需分配。
3. 最多同时打开 4 个项目索引；LRU 关闭连接并保留磁盘数据库，下次重新校验。
   所有项目共用一个构建线程。旧共享索引原位保留，首次使用新目录从源码重建，
   不改 registry、源码、凭据、写入恢复和业务数据库。
4. 每库 DELETE 日志的保守临时磁盘额度为 1,500 MiB；这是主库/日志的磁盘预留规则，
   不预分配这些空间。原文件/解析内容仍 32 MiB、逻辑索引 48 MiB、事实 200,000。
   SQLite 页缓存仍约 2 MiB；没有宣称整个应用存在 500 MiB RSS 硬限制。
5. 内容防护排除状态稳定时，可复用未变化文件的关系。拓扑指纹额外包含排除文件
   的元数据；排除状态/文件变化、拓扑/来源变化、扫描或容量受限仍重新绑定。
   输出继续标记 `index_partial`，不关闭内容防护或将部分覆盖冒充完整覆盖。
6. 删除服务入口与包装层之间的重复哈希校验。稳定结构请求从四轮变为三轮哈希
   校验，保留查询前后完整目录、已观察源码、来源身份、撤权和写入恢复检查。
7. 容量失败响应提供当前页数、上限、发布阶段和最后完成表的页数下界。
   不把事务回滚后的页数当失败瞬时峰值；不回显源码、SQL 输入或凭据。

## 单库与模块分片方案选择

| 方案 | 当前约 240 文件项目 | 十万/三十万文件目标 |
| --- | --- | --- |
| 每项目 500 MiB 单库 | 改动较小，现有查询与原子发布可直接复用，适合本轮修复 | 仍受文件发现、解析对象、事实数与校验遍历限制 |
| Catalog＋模块 SQLite 分片 | 需要路由、跨片绑定、失效和发布协议，不能仅拆数据库文件 | 更适合按需构建和分批释放，但需要规模实测 |

SQLite 本身按页读取，单库磁盘额度不等于把整库读入内存，见
[SQLite 页缓存文档](https://www.sqlite.org/pragma.html#pragma_cache_size)。
分片要降低内存，还需把当前全项目 `parsed_files` 和 `Resolver` 改成分批流程。

后续模块分片第一阶段应先做两三个模块，验证跨片调用、继承、反向引用与影响分析，
再扩大模块数。Catalog 需要记录导出符号、反向依赖和一致的发布代次；分片总磁盘额度、
目录与打开连接数也要有界。分别提交多个连接不自动具备跨库原子性；SQLite 的
[ATTACH 事务规则](https://www.sqlite.org/lang_attach.html) 有特定条件。
官方 [ATTACH 上限](https://www.sqlite.org/limits.html#max_attached) 默认 10 个，
大规模路由不应依赖一次挂载所有分片。

模块分片及十万/三十万文件支持尚未实现。

### 5,000 文件基准

同一机器、同一源码夹具，每个 Python 文件一个定义，另含 Java 等辅助文件；五次
连续查询取中位数。三次独立运行均通过各自的所有检查，且运行期间相关源码未变化。
首次指新进程与空索引，不清 OS 文件缓存；计时不含 desktop、MCP 隧道或模型调用。

| 指标 | build 18 源码，旧 64/128 MiB 配置 | 本轮源码，旧 64/128 MiB 配置 | 本轮实际 500/1500 MiB、每项目单库 |
| --- | ---: | ---: | ---: |
| 首次结构查询 | 2,712.478 ms | 2,779.855 ms | 2,632.287 ms |
| 连续查询中位数 | 599.426 ms | 504.956 ms | 510.078 ms |
| 增加定义后的单文件更新 | 1,522.926 ms | 1,467.832 ms | 1,479.040 ms |
| 重启后检测离线修改 | 2,691.145 ms | 2,587.017 ms | 2,590.325 ms |

旧配置同条件连续查询减少约 15.8%，本轮实际配置减少约 14.9%；首次构建没有稳定的
显著加速结论。新增函数体更新用例仅解析/重新绑定 1 个文件，复用 5,003 个文件关系，
实际配置总请求为 2,685.334 ms。仍需重写当前版索引表及完整源码新鲜度校验，关系复用
不等于 SQLite 原位增量更新，也不意味着每种编辑都比全量绑定更快。

当前配置合成基准进程 RSS 高水位约 116.9 MiB，来源为 `getrusage`；包含全部进程组件，
不是应用的内存硬上限，也不是大型企业项目成绩。监听、旧上下文拒绝、未查询项目
按需不建库、离线修改及数据库完整性均通过。

原始基准分别保留在 `.artifacts/live-benchmark.9fb572/`、
`.artifacts/live-benchmark.56e9c4/`、`.artifacts/live-benchmark.1c0724/`。

### 存储与恢复语义

每次发布在单库事务中替换该项目的旧记录，外键级联清除旧文件、解析及关系记录，
不会积累历史版本。旧物理页作为 SQLite 空闲页复用；删除记录不会承诺文件立即缩小。
LRU 只关闭空闲连接，磁盘项目数据库保留，下次使用先检查当前源码。
500 MiB 是每项目主数据库的磁盘上限，4 是同时打开的连接数，不是磁盘项目数量上限。

首选恢复标签继续固定在 `9150904`，本轮提交不替代它。原有用户文档及四个样例目录
保留；本轮证据与构建产物保留。仅已被替换且无运行进程引用的 build 18 应用副本在
新版验收后采用废纸篓方式清理，具体路径记录在安装报告。
