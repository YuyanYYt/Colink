## 确认并修复的问题

1. **解析缓存损坏后反复构建失败。** CP1 解压失败原来进入 `INDEX_BUILD_FAILED`，
   下一次仍复用同一坏缓存。现在只重新读取和解析受影响的文件，保留其他有效解析。
2. **关系缓存损坏抛出底层异常。** CL1 解压错误原来直接抛出 `zlib.error`。
   现在返回有结构的 `INDEX_CACHE_INVALID`，使该项目关系失效；下一次查询或重启后
   从有效解析重建，不把破损关系再次复用，不回显载荷或底层异常文本。
3. **回退时旧格式标记错误。** 压缩解析缓存原来仍标为旧 `PARSER_VERSION`。
   真正运行 9150904 会将其当 JSON 解析并持续失败。新缓存使用 `live-packed-v1-*`，
   新版兼容历史 JSON 和早期 CP1，旧版跳过新标记后重建。已在独立样例上实际运行
   9150904，确认可重新生成索引。大缓存超过旧页数上限时仍应先保留再重建，见
   [恢复说明](RECOVERY_9150904.md)。
4. **逻辑预算仍阻碍可容纳的索引。** 真实仓库修复前触及 100,000 解析事实和
   32 MiB 索引内容限制；扩大预算的隔离探测确认物理数据库仍能容纳。
   新 live 限额为 200,000 事实和 48 MiB 索引内容；主数据库仍 64 MiB、磁盘临时
   预算 192 MiB，源码/解析内容仍 32 MiB，镜像历史索引的预算保持原值。
5. **查询重复验证。** 每次结构查询原来重复做五次上下文指纹校验和五次目录清单
   遍历。删除重复工作后保留四次指纹校验、三次清单遍历，查询前后、构建发布前
   仍完整校验已观察文件、文件清单和来源身份；包装层仍重查授权和待恢复写入。
   监听提示、mtime 缓存或时间缓存不替代上述检查。
