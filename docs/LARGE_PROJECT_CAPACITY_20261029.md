# Live 大项目容量扩展与验证 · 2026-10-29

本文记录 2026-10-29 的扩容设计与实测，相关源码已纳入 0.5.0。容量按需分配，
实际验证规模见下文。

## 容量配置与实际生效路径

| Live 项目预算 | 原默认 | 新默认 large | 本机可选 extreme |
| --- | ---: | ---: | ---: |
| 文件数 | 50,000 | 250,000 | 1,000,000 |
| 发现目录数 | 10,000 | 100,000 | 500,000 |
| 源码字节 | 32 MiB | 512 MiB | 2 GiB |
| 解析载荷 | 32 MiB | 256 MiB | 1 GiB |
| 索引载荷 | 48 MiB | 256 MiB | 1 GiB |
| 解析/结构事实各自上限 | 200,000 | 2,000,000 | 10,000,000 |
| 数据库物理页 | 500 MiB | 2 GiB | 8 GiB |
| 主库及日志临时峰值预算 | 1500 MiB | 6 GiB | 24 GiB |
| 清单发现时间 | 5 秒 | 30 秒 | 60 秒 |

`live_capacity.py` 统一保存本机预设，`ProjectIndexService` 将各预算传给单项目
`LiveIndexService`。独立 `live` 与多项目 `workspace` 提供 `--capacity large|extreme`，
菜单栏源码默认使用 large。网页 MCP 不能更改容量档或扩大目录授权。磁盘只按实际
使用分配；临时峰值预算是物理页上限的保守三倍，不会在启动时预占这些空间。

`connection_status` 报告容量与最多八个已授权项目的索引用量样本；未请求过的索引
不因此创建数据库。样本显示是否需要源验证，不能当作当前源码已验证的索引状态。
索引状态按 source/parse/index 字节、解析/结构事实、文件、目录、物理数据库
分别返回 `used/limit/percent`。超限计数使用 `budget_exceeded_files` 指明实际资源，
并保留兼容的 `PROJECT_*_BUDGET_EXCEEDED` 诊断。清单发现受限单独报告文件数、
目录数、目录项或时间原因。磁盘容量不会被解释为进程内存上限。

文本搜索的每页扫描字节上限从 128 MiB 增至 512 MiB，仍受请求时间预算及续读
协议控制。单文件继续为 4 MiB，源码/图单次响应继续最多 50,000 字符；单文件
符号、引用和语法节点限制保持原值。指纹与 AST 缓存继续有界，索引仍单工作线程。
文件极大、语言不支持、源码被排除及动态解析不确定性均不由项目容量扩容消除。

容量参与 Live 索引版本签名，升级后按需重建派生事实；旧镜像的上传/存储预算、
源码和写入恢复数据不变。所有本轮运行均使用新目录，没有打开正在使用的安装版
数据库，没有执行旧索引原地迁移；原有恢复与小磁盘失败相关测试单独运行。

## 架构图续取与建议落实情况

Live `get_project_architecture` 的单页节点/边请求上限改为 5000/10000，默认仍为
100/200。首次请求正常返回 `snapshot`、`graph_id`、`next_cursor`、文件/边偏移、
`total_files/total_edges` 和 `has_more_files/has_more_edges`；继续使用同一 snapshot、
筛选条件与 next_cursor。max_chars 及外层 display_name 造成裁剪时，继续位置按
实际返回项重算。一个完整项也放不下时明确返回容量错误，不返回无法推进的游标。

文件和边各自遍历整个查询范围，边不受当前页已选节点限制；端点可能在别的文件页，
按 path/source/target 合并即可保留跨页面、跨模块边。`path_prefix` 仍代表范围内
子图，跨该范围的边不包含在子图中。SQL 提前筛选路径，避免子图加载无关关系。
图游标绑定当前源身份、清单、索引版本和图内容，源码值变化但图拓扑相同时也会拒绝
旧游标，返回固定 `STALE_ARCHITECTURE_CURSOR`。历史 Mirror 默认图语义保持兼容。

大 SCC 不再为每个文件重复全部成员：每个文件携带稳定 `cycle_group_id`、成员
总数和有界样本，样本最多 32 条且不超过 2048 字符。全部文件页中相同组标识可
重组完整成员。`cycle_summaries_truncated` 明确区分样本未完整展示与节点/边尚未
取完；`next_cursor=null` 只表示当前索引图已取完，不能证明底层源码索引完整。

对照“判断项目图覆盖处理”的建议，本轮落实了容量及超限诊断、覆盖状态、真实游标
分页、跨页边保留、稳定标识、源状态变化拒绝，以及合并完整性测试。运行产品尚未
提供自动巡回补索引、自动收集和合并所有图页、按模块/连通区自动分片、全局模块
概览及下钻视图；这些不能以分页接口或测试中的合并逻辑代称已经实现。索引仍有
缺失时继续报告 unknown/partial，不用空关系宣称没有依赖。

## 独立容量验收

使用 `uv run python scripts/verify_large_capacity.py` 运行。本脚本只在当前仓库
`.artifacts/capacity-<时间>-<随机值>/` 新建独立源码副本、合成工程和派生数据库；
所有产物保留。真实源码的两个场景使用同一份复制的生产模块，旧场景显式设置
原有 32 MiB 源码、32 MiB 解析、48 MiB 索引、200,000 事实和 500 MiB 数据库预算，
新场景使用扩容后的默认值。每个场景在独立进程内记录峰值 RSS。

正式通过记录在 `.artifacts/capacity-20261029T090356Z-29a8c6bc/`，包含
`source-manifest.json`、逐场景 JSON、标准错误记录、`report.json`、`report.md`、
独立源码副本、合成文件和三个数据库。源码清单保存逐文件 SHA-256，报告记录清单
总哈希、Python 和操作系统信息。

| 场景 | 文件 | 结构事实 | 项目容量受限文件 | 首次查询秒数 | 峰值 RSS MiB | 数据库 MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 当前真实源码，旧预算 | 346 | 102,408 | 38 | 6.605 | 220.2 | 65.6 |
| 同一真实源码，新默认 | 346 | 119,434 | 0 | 7.052 | 238.6 | 76.3 |
| 合成 Python 源码，新默认 | 300 | 240,300 | 0 | 14.004 | 522.4 | 152.7 |

真实源码的旧预算复现了 26 个 `PROJECT_INDEX_BUDGET_EXCEEDED` 和 12 个
`PROJECT_PARSE_BUDGET_EXCEEDED` 文件，新默认下这 38 个文件全部恢复，结构 ready
文件数从 187 增至 225。仍有四个源码正文排除文件和四个 JavaScript 部分解析文件，
因此全项目 `partial` 继续为真；扩容没有把访问排除或语言解析限制冒充完整索引。
这份隔离复制的文件清单与先前网页会话不同，不能把 38 与其 48 个受限文件直接等同。

合成场景包含 300 个 Python 文件，每文件 200 个函数，合计 60,000 个函数；
实际保存 60,300 个符号和 180,000 条关系，即 240,300 条结构事实。解析事实数
为 420,600，解析载荷约 58.8 MiB，索引载荷约 105.9 MiB。300 个文件均 ready，
没有项目预算诊断，三个数据库的 SQLite `integrity_check` 均为 `ok`。

另一个纯发现场景创建 50,001 个空 Python 文件，分布在 52 个目录。显式旧文件
预算只发现 50,000 个并返回 `partial=true`；新默认发现完整 50,001 个，
`partial=false`，约 0.703 秒，正文读取数为零。该场景没有进行五万文件结构解析，
不可据此声称已完成五万真实源码文件索引。

重启验证重新创建 `SourceAccess` 和索引服务，复用同一个新数据库，约 0.224 秒。
提取调用数为零，没有事实重发布，事实总量保持 119,434；为验证当前源码仍进行
234 次正文读取。这是源验证与索引复用的实际行为，不声称重启后完全无源文件 I/O。

基准将结构构建等待时间设置为 600 秒、清单扫描时间设置为 120 秒，避免基准把
异步等待或发现时间预算误认为容量失败；它不验证默认查询的完成时间保证。
报告中的这些参数是基准覆盖值，生产默认扫描时间另由容量配置提供。

首轮 `.artifacts/capacity-20261029T090247Z-3810c736/` 也保留：当时错误地用
“重启正文读取数为零”判断复用，唯一失败项是这一验收断言，其余容量检查通过。
修正为直接观察提取调用与事实重发布后完成上述正式复跑；没有删除失败记录。

本轮规模检查证明旧预算瓶颈得到解除，并实际越过旧的 50,000 文件发现和
200,000 结构事实阈值。它没有验证 250,000/1,000,000 文件的完整解析、
2,000,000/10,000,000 事实的内存峰值，也不替代公网部署或 ChatGPT 网页验收。
