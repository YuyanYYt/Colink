# 本机项目工作区与清理

设置 → 存储位置 → 项目数据按本机工作区显示。每个工作区对应一次选中的源码目录，
保存在 `<存储位置>/.code-context/desktop/workspaces/<源码目录路径的 SHA256>/`。
一个工作区可以登记多个项目。包含多个项目的工作区只显示一行，确认清理前显示
项目数量、名称及完整位置，避免误把同一目录下的其他项目一并清理。

工作区包括 `tunnel/profile.yaml` 和 `live-v1/`：后者的 `registry/` 是项目登记，
`index/projects/<项目 ID 的 SHA256>/` 是当前每项目代码索引，`terminal-v1/` 保存
终端回执与进程监督信息，`execution-v1/` 保存可选隔离执行的账本、任务、端口与
依赖缓存，`git-v1/` 保存 Git 操作准备材料。`database-profiles/` 可能是旧数据库
接入留下的配置。列表显示全工作区文件长度及分配磁盘空间；稀疏镜像的两者可能
差别很大。列表只读文件元数据与项目登记，不打开或初始化索引数据库。

清理工作区需要先关闭连接。后台核对目录、文件所有权、无链接边界、运行与索引
账本锁、进程监督状态及全局写入恢复状态。仍被使用、存在未完成写入恢复、挂载
卷、链接、未知内容或无法核对的数据保持原样。可清理时，整个工作区先在同卷
`retired-workspaces/` 中停用，然后由原生 macOS FileManager 移到废纸篓；系统动作
失败会保留具体停用路径，不永久删除。清理包含项目登记、新旧索引、专属配置与
已结束任务的本机派生数据；清理后该工作区及其项目从列表中消失。

原始源码、源码目录内的依赖与业务数据库、全局连接配置和
`.code-context/write-recovery-v1/` 保留。后者是多个工作区共用的写入恢复库，不属于
所选工作区目录。清理只在本机明确点击时执行，不增加 MCP 工具、写入审批或核心
运行限制，也不自动运行项目代码。

重建：重新选择仍存在的源码目录并启动连接，生成新的项目登记和本机运行工作区；
第一次结构分析按需建立索引，普通文件读取和终端不依赖代码索引。多项目需要按
现有本机流程重新启用，清理前的写入/开发授权不会自动恢复。

恢复：从废纸篓取出 `CoLink-workspace-...`，根据其中
`live-v1/registry/projects.json` 的 `workspace.path` 计算原路径 SHA256，将整个目录
复原到上述 `workspaces/<SHA256>/`。如果该位置已因重建存在，先保留两份数据，不
覆盖合并。Finder“放回”可能恢复至停用暂存位置，之后仍需复原到工作区原位置。
恢复不会启动连接或重新授予开发权限。

本次操作结果包含工作区名称和恢复说明，重新打开、刷新或翻页清除旧结果，避免把
历史清理提示误认为当前状态。build 31 按用户确认移除重复的底部静态恢复说明。

旧的 `index/live-index.sqlite3` 与当前 `index/projects/` 是两种索引布局；外层工作区
本身属于当前多项目架构。显式离线迁移验证旧数据库后，把登记仍匹配的事实分到
每项目数据库，保留现有新索引，并可恢复地停用旧数据库。迁移不放在每次查询、
应用启动或监听流程中；损坏或无法确认的旧数据保留并报告。

数据流边界：结构索引持久化；M2 Python 数据流的 AST、调用上下文、临时节点与边
仅在请求内使用，没有持久化完整数据流图或方法摘要。本维护版保持此策略。
